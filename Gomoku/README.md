# 五子棋 AI 对战（BFS 策略树 vs Minimax + α-β 剪枝）

让两套**互相独立**的五子棋 AI 在同一程序里自动对弈，并通过网页实时观看：

| 执子 | 算法 | 搜索方式 | 每手耗时（实测参考） |
|---|---|---|---|
| 黑方（先手） | 自研 **BFS 策略树** | 两层全展开建树 + DFS 回溯取值 | 约 0.9 秒 |
| 白方（后手） | DeepSeek **Minimax + α-β 剪枝** | 深度 4、迭代加深、1.5 秒限时 | 首手 15ms，随局面复杂度上升 |

- 棋盘 15×15，无禁手，五连即胜，下满 225 手判平局，黑先行。
- 两套算法的核心逻辑**逐字保留、未做任何改动**，接入对战框架只新增适配层（见第 7 节）。

## 4. 系统架构

```text
浏览器（canvas 棋盘 + 控制面板 + 对局记录）
        │ HTTP（JSON）
        ▼
httplib Server :8080（全局互斥锁）──► Battle 对战调度
   ├─ GET  /            返回内嵌对战页面
   ├─ GET  /api/state   读取当前局面
   ├─ POST /api/step    走一手（同步计算）：
   │       ├─ 黑 → userAIMove()                 → BFS 策略树 + DFS 回溯
   │       └─ 白 → DSEngine.getBestMovePublic() → Minimax + α-β（深度 4）
   └─ POST /api/reset   重开一局
```

一次落子的完整链路：前端 `POST /api/step` → `Battle::step()` 按手数奇偶决定执方（第 1、3、5… 手黑，第 2、4、6… 手白）→ 调用对应算法得到落点 → 写入棋盘 → `checkWin` 判胜并记录获胜五连坐标 → 返回最新局面 JSON → 前端重绘。

## 5. 黑方算法：BFS 策略树（Gomoku_strategy_tree.cpp）

### 5.1 搜索框架

1. **建树（BFS）**：`constructTree` 从当前局面出发，用 `deque` 队列逐层扩展两层（`DEPTH = 2`）。每个节点枚举棋盘上全部空位作为子节点，奇偶层交替执子（我方 / 对方）。
2. **叶子估值**：最深层（`depth == DEPTH - 1`）现场评估双方棋盘分，`val = 己方评分 − 对方评分`；上层节点先置哨兵值（我方层 `INT_MIN`、对方层 `INT_MAX`），待回溯时覆写。
3. **取值（DFS 回溯）**：`traverseDecisionTree` 按 minimax 规则回溯 —— 我方层取子节点最大值、对方层取最小值；第 0 层更新最优值时，把该最优子节点的整盘棋存入全局 `bestBoard`。
4. **兄弟排序**：子节点按"分值降序，同分按 `aroundScore`（落点周围 8 格邻子数）降序"排序，决定同分候选的取舍顺序。

### 5.2 评估函数（字符串棋形匹配）

- `getLineString` 把一条线抽成字符串：`'1'` = 己方、`'0'` = 空、`'2'` = 对方或边界墙，两端各补一个 `'2'`；`isEnemy` 参数控制视角翻转（1 与 2 互换）。横、纵、两条对角共覆盖 72 条线（长度不足 5 的斜线跳过）。
- `fastDict` 棋形表逐模式匹配，`left` / `right` 边界字符集用于区分**活形与眠形**：

| 棋形（归纳） | 模式示例 | 分值 |
|---|---|---|
| 连五 | `11111` | 10,000,000 |
| 活四 | `011110` | 1,000,000 |
| 冲四 / 活三变体 | `011112` `11110` `011101` `101110` | 10,000 |
| 活三 / 跳活三 | `01110` `010110` `011010` | 5,000 |
| 活二类 | `001100` `011000` `000110` `010100` | 500 |
| 弱二 | `110000` `000011` | 250 |

- 命中并计分后，用 `line.replace(...)` 把该段替换为 `'2'` **屏蔽已计分区域**，防止同一段棋子被更长或更短的模式重复计分。
- 兜底：剩余零散棋子每颗计 10 分。

### 5.3 坐标约定（对接必读）

全程统一 `board[y][x]`：**外层下标是行 y，内层下标是列 x**。HTTP JSON 与前端绘制均以 x 为列、y 为行。适配层提取落点时用"算法输出棋盘 vs 输入棋盘"整盘 diff，恰好相差 1 格即为落点——天然规避了算法内部 `(x, y)` 命名语义差异带来的坐标轴混乱问题。

### 5.4 复杂度与局限

- 每手重建整棵树：空盘首手为 225 × 224 ≈ **5 万个叶子评估**，实测约 0.9 秒/手（随棋子增多略降，视机器性能而定）。
- 全展开、无剪枝、深度仅 2，只能看到"我下一步 + 对手回应"这一个来回。
- 若需加深，可参考 α-β 剪枝重构版（深度优先 + 候选裁剪 + 启发式排序，评估函数完全不变，`alphabeta_gomoku.cpp`），深度提到 4 后耗时降至毫秒级。

## 6. 白方算法：Minimax + α-β（DSEngine，位于 Gomoku_ai_vs_ai_v1.cpp）

### 6.1 评估函数 `evaluate()`

沿 4 个方向线扫描，统计每段同色连子数 `count` 与开放端数 `openEnds`：

| 棋形 | 条件 | 分值 |
|---|---|---|
| 五连 | count ≥ 5 | 1,000,000 |
| 活四 | count = 4，两端皆空 | 100,000 |
| 眠四 | count = 4，单端空 | 10,000 |
| 活三 | count = 3，两端空 | 5,000 |
| 眠三 | count = 3，单端空 | 500 |
| 活二 / 眠二 | count = 2 | 100 / 10 |

总分 = AI 分 − 1.2 × 对手分（防守权重略高于进攻）。

### 6.2 候选生成与搜索

- `generateMoves()`：取所有已有棋子周围 2 格内的空位（去重）；空盘时下天元。
- `getBestMove()`：根候选按"离中心曼哈顿距离"升序排序（先搜中心附近的点，剪枝更早生效）；**迭代加深** d = 2 → 4，即使深处超时也保有上一深度结果；`TIME_LIMIT_MS = 1500` 在根候选之间检查超时，超时立即返回当前最优。
- `minimax()`：标准 α-β 剪枝；落子即成五连直接给 ±1,000,000 并提前返回，不再继续展开。
- 对外接口：`loadBoard()` 拷入对战棋盘；`getBestMovePublic()` 返回 `{x, y}`（x = 列，y = 行）。引擎恒执白（`AI_COLOR = 2`）。

## 7. 对战调度与适配说明（算法核心零改动）

对接时仅做了以下适配，双方算法本体逐字未动：

1. **剥离 `main`**：两套算法各自去掉入口函数，由 `Battle::step()` 统一调度，按手数奇偶轮流执子。
2. **黑方适配 `userAIMove()`**：把对战棋盘的 0 / 1 / 2（空 / 黑 / 白）映射为算法视角的 0 / 1 / −1（己方 1、对方 −1）；建树回溯后用 `bestBoard` 与输入棋盘做整盘 diff 求落点，并校验"恰好相差 1 格且该格为空"。
3. **白方适配**：DeepSeek 原框架的 `Game` 类改名为 `DSEngine`（避免与对战层 `Battle` 的状态混淆），新增 `loadBoard()` 与 `getBestMovePublic()` 两个公开入口，内部搜索与评估逻辑未动。
4. **补 `deleteTree()`**：黑方算法每手重建策略树，新增递归释放函数，防止长期对局内存泄漏（原独立版未释放树内存）。

胜负判定在 `Battle` 层完成：五连即胜并记录获胜五连坐标供前端高亮；下满 225 手平局；若某算法返回非法着法（越界、占位、失败），兜底判对方胜——正常对局不会触发。

## 8. HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 对战页面（单页 HTML，随源码内嵌） |
| GET | `/api/state` | 获取当前完整状态 JSON |
| POST | `/api/step` | 当前执方走一手（同步计算，可能阻塞数秒），返回最新状态 JSON |
| POST | `/api/reset` | 清空棋盘并重置双方引擎，返回初始状态 JSON |

**状态 JSON 结构**（实际响应中均为单行，此处展开便于阅读）：

```json
{
  "board": [[0,0,...]],        // 15×15 二维数组：0 空 / 1 黑 / 2 白，board[y][x]
  "moveCount": 2,              // 已下手数
  "lastX": 7, "lastY": 7,      // 最后一手坐标（x=列, y=行），尚无落子时为 -1
  "lastColor": 2,              // 1 黑 / 2 白，尚无落子时为 -1
  "lastMs": 15,                // 最后一手耗时（毫秒，取整）
  "gameOver": false,           // 对局是否结束
  "winner": 0,                 // 0 进行中 / 1 黑胜 / 2 白胜 / 3 平局
  "winCells": [],              // 获胜五连坐标 [[x,y],...]，供前端高亮
  "moves": [                   // 逐手记录
    {"n":1, "c":1, "x":5, "y":10, "ms":896},
    {"n":2, "c":2, "x":7, "y":8,  "ms":15}
  ]
}
```

curl 示例：

```bash
curl http://localhost:8080/api/state
curl -X POST http://localhost:8080/api/step   # 走一手
curl -X POST http://localhost:8080/api/reset  # 重开一局
```

## 10. 已知问题与注意事项

1. **黑方耗时与内存**：两层全展开约 5 万叶子/手，实测约 0.9 秒/手，且每手新建整棵树（节点带整盘棋拷贝，内存开销大）；`deleteTree` 已保证不泄漏，但提速需改用 α-β 重构版。
2. **白方限时粒度**：超时检查只发生在根候选之间，单个根候选的深层搜索不可中断，复杂局面下单手可能明显超过 1.5 秒（源码注释标注极端情况约 25 秒）。
3. **同步 API**：`/api/step` 计算期间请求持续等待，前端不要给它设置过短的超时；期间其他请求因全局互斥锁会排队等待。
4. **独立版编译修复**：`Gomoku_strategy_tree.cpp` 需按第 3.1 节补 `#include <climits>` 并补全 `getNewNode` 调用参数后方可编译；对战主程序无此问题。
5. **独立版 `main` 无输出**：它只做"能编译、能跑通"的冒烟测试；想看具体落点可自行打印，或直接使用对战程序观察。
6. **端口安全**：服务监听 `0.0.0.0`，公网部署请自行增加访问控制，或改为监听 `127.0.0.1`。
