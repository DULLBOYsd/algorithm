# 五子棋 AI 对战（自研算法三代演进 × DeepSeek Minimax · 可插拔 + 人机对战）

让两套**互相独立**的五子棋 AI 在同一程序里对弈，并通过网页实时观看。自研算法历经三代迭代（BFS 决策树 → DFS + α-β 剪枝 → 成五短路 + 四威胁点强制候选），对战框架同步迭代三代（固定对阵 → 三算法可插拔 → 四模式 + 人机对战）：

| 执子 | 可选算法 | 搜索方式 | 每手耗时（实测参考） |
|---|---|---|---|
| 黑 / 白均可 | 自研 **BFS 决策树**（第一代） | 两层全展开建树 + DFS 回溯取值 | 约 0.9 秒 |
| 黑 / 白均可 | 自研 **DFS + α-β 剪枝**（第二代） | 深度 3、候选半径 2、启发排序 | 约 1–3 秒 |
| 黑 / 白均可 | 自研 **α-β 三代增强版**（当前主力） | 深度 4 + 成五短路 + 四威胁强制候选 | 约 1–5 秒（劣势局极端可达 10–20 秒） |
| 黑 / 白均可 | DeepSeek **Minimax + α-β**（DSEngine） | 迭代加深 2→6、1.5 秒限时 | 首手 15ms，随局面复杂度上升 |
| 黑 / 白均可 | **human**（玩家本人） | 页面点击落子 | 0 |

- 棋盘 15×15，无禁手，五连即胜，下满 225 手判平局，黑先行。
- 三代算法的搜索与评估逻辑均保留原设计；框架内嵌副本仅包含已验证的勘误修正（见第 10 节同步修改提醒与第 11 节第 1 条），接入对战框架只新增适配层（见第 8 节）。
- 默认对阵：黑 = 第一代 BFS，白 = DeepSeek Minimax（与最初版本一致，便于对照历史行为）。

## 1. 三代演进总览

### 4.2 页面操作（v3）

| 控件 | 行为 |
|---|---|
| 黑方 / 白方算法下拉框 | 各自选择 bfs / alphabeta / deepseek / human，点「重新开始」后生效 |

## 5. 系统架构

```text
浏览器（canvas 棋盘 + 算法下拉 + 控制面板 + 对局记录）
        │ HTTP（JSON）
        ▼
httplib Server :8080（全局互斥锁）──► Battle 对战调度
   ├─ GET  /            返回内嵌对战页面
   ├─ GET  /api/state   读取当前局面（含双方算法配置）
   ├─ POST /api/step    走一手（同步计算）：
   │       ├─ bfs       → BFSAlgo.move()                 → BFS 决策树 + DFS 回溯
   │       ├─ alphabeta → ABAlgo.move()                  → DFS + α-β（三代增强，深度 4）
   │       ├─ deepseek  → DSEngine.getBestMovePublic()   → Minimax + α-β（迭代加深）
   │       └─ human     → 使用请求携带的 x/y 坐标（带合法性校验）
   └─ POST /api/reset   按参数配置双方算法并重开一局
```

一次落子的完整链路：前端 `POST /api/step`（human 轮附加 `?x=&y=`）→ `Battle::step()` 按手数奇偶决定执方（第 1、3、5… 手黑）→ 查该方算法配置并调用对应入口 → 写入棋盘 → `checkWin` 判胜并记录获胜五连坐标 → 返回最新局面 JSON → 前端重绘；若失败则在 JSON 末尾附加 `err` 字段。

## 6. 自研算法三代详解

### 6.1 第一代：BFS 决策树（Gomoku_strategy_tree.cpp）

**搜索框架**：

1. **建树（BFS）**：`constructTree` 从当前局面出发，用 `deque` 队列逐层扩展两层（`DEPTH = 2`）。每个节点枚举棋盘上全部空位作为子节点，奇偶层交替执子（我方 / 对方）。
2. **叶子估值**：最深层现场评估双方棋盘分，`val = 己方评分 − 对方评分`；上层节点先置哨兵值（我方层 `INT_MIN`、对方层 `INT_MAX`），待回溯时覆写。
3. **取值（DFS 回溯）**：`traverseDecisionTree` 按 minimax 规则回溯——我方层取最大、对方层取最小；第 0 层更新最优值时，把该最优子节点的整盘棋存入全局 `bestBoard`。
4. **兄弟排序**：子节点按"分值降序，同分按 `aroundScore`（落点周围 3×3 邻子数）降序"排序。

**评估函数（字符串棋形匹配）**：

- `getLineString` 把一条线抽成字符串：`'1'` = 己方、`'0'` = 空、`'2'` = 对方或边界墙，两端各补一个 `'2'`；横、纵、两条对角共覆盖 72 条线。
- `fastDict` 逐模式匹配，`left` / `right` 边界字符集区分**活形与眠形**：

| 棋形（归纳） | 模式示例 | 分值 |
|---|---|---|
| 连五 | `11111` | 10,000,000 |
| 活四 | `011110` | 1,000,000 |
| 冲四 / 活三变体 | `011112` `11110` `011101` `101110` | 10,000 |
| 活三 / 跳活三 | `01110` `010110` `011010` | 5,000 |
| 活二类 | `001100` `011000` `000110` `010100` | 500 |
| 弱二 | `110000` `000011` | 250 |

- 命中并计分后，用 `line.replace(...)` 把该段替换为 `'2'` **屏蔽已计分区域**，防止同一段棋子被重复计分；剩余零散棋子每颗计 10 分。

**坐标约定（对接必读）**：全程统一 `board[y][x]`（外层行、内层列）；HTTP JSON 与前端绘制以 x 为列、y 为行。BFS 适配层提取落点用"算法输出棋盘 vs 输入棋盘"整盘 diff，恰好相差 1 格即为落点——天然规避算法内部 `(x, y)` 命名语义差异。α-β 系算法的适配层则直接输出 `(行, 列)`，第一维=行、第二维=列，与主棋盘 `board[行][列]` 一致。

**复杂度与局限**：每手重建整棵树，空盘约 5 万叶子评估、实测约 0.9 秒/手；全展开、无剪枝、深度仅 2，只能看到"我下一步 + 对手回应"。

### 6.2 第二代：DFS + α-β 剪枝（alphabeta_gomoku.cpp）

保持评估函数逐字不变，把搜索框架重构为深度优先：

1. **先落子再分支**：`alphabeta(board, possiblePos, alpha, beta, row, col, depth)` 入口先落子、扩展候选，再递归；`depth == DEPTH` 时返回 `getNowVal(我方) − getNowVal(对方)`。
2. **候选生成**：`fillPossiblePos` 把已有棋子周围 2 格内的空位标记为可能落点（半径 2，中盘候选可达 60+）；另设**空盘天元特判**（第一手直接下 (7,7)）。
3. **启发排序**：候选按 `aroundScore`（3×3 邻子数）降序排序后再递归，让剪枝更早生效。
4. **窗口传递**：我方层 `v` 初值 `INT_MIN`、对方层 `INT_MAX`（按最坏可能初始化），每层只做一次 `alpha/beta` 更新与 `beta <= alpha` 剪枝判断，窗口沿递归累积传递。
5. **根层全展开**：`getBestPos` 遍历全部候选各做一次以 `bestV` 为下界的搜索取最大——根层不做 topK 截断，保证任何候选都不会被漏掉。

深度提到 4 后，剪枝使每手节点数大幅下降，独立版毫秒~秒级可用。**框架 v2 内嵌版取 `DEPTH = 3`**：当年深度 4 在 15×15 中盘（60+ 候选）单手可达 300 秒以上，不可实战；深度 3 经金标准验证同样正确、中盘约 1–3 秒。这一瓶颈直到第三代引入成五短路 + 威胁剪枝后才解除。

### 6.3 第三代：成五短路 + 跳冲四棋形 + 四威胁点强制候选（Gomoku_strategy_tree_v3.cpp）

在第二代框架上做三项增强，分值体系升级为 long long：

**（1）成五短路 `absoluteResult(board, row, col, color)`**

落子后立即沿 4 个方向双向数连子，≥5 连直接返回 `±INT_MAX` 终局分，不再展开该分支：

- 终局分与评估分隔离：五连的价值不再经由 `fastDict` 的 1000 万分参与中间层比较，避免"双方各差一子成五"之类的双五局面在评估里互相抵消、污染上层决策；
- 只判五连，活四不在此判（活四仍留给评估函数，由搜索层处理）；
- 对照实验：同型对杀局面关闭短路会误选必败点，分值恶化 30 倍以上；开启后同时省去无谓展开。

**（2）`fastDict` 补 11011 跳冲四**

`11011`（跳冲四：五格窗口 4 子 1 缺口）原先匹配不到任何棋形条目，只按零散子得 40 分——对一个"下一手即成五"的致命棋形低估了 2500 倍，导致搜索层几乎完全忽视跳冲四的攻防。修复：字典新增 `{"11011", "", "", 100000}`（与冲四族同档）。回归验证其余全部棋形分值不变、死棋形不误判。

**（3）checkFour / pushFour：四威胁点强制候选**

- **根因**：候选按 `aroundScore`（纯几何邻子数）降序取前 15 后，真正致命的成五点/防点天然"冷门"——实战案例中黑方冲四唯一活点 (3,4) 的 aroundScore 只有 1，被热闹区（around 6–8）挤出 top15，导致递归层根本看不到"对方下这里就赢"，成五短路也就永远没有触发机会。开关对照实验：同一局面关掉 topK 后短路触发 15134 次，开着 topK 只有 76 次（200 倍差距），实锤截断是漏判根源。
- **`checkFour(board, row, col, color)`**：判定 color 方落子于 (row,col) 后，该方向上"连续己方子数 cnt + 至多一个末端空位 space ≥ 5"（即形成了冲四及以上威胁，包括落子直接成五、眠四延伸，以及**已有 11011 跳四的成五缺口**——缺口两侧都有己方子时 cnt 可累到 5）。方向扫描遇对方子或边界即停，正反两遍覆盖缺口在任一侧的情形。
- **`pushFour(board, cands, existFour)`**：把候选扫描阶段检出的全部威胁点 `existFour` 与 `cands` 的前 15 名合并去重（`std::set`），按 `aroundScore` 降序排序，作为本层的分支数组。效果：**威胁点不受 topK 配额限制，永远参与搜索**；正常候选仍保留前 15 控制分支数。
- **双向检查（关键）**：每层收集候选时对每个空位同时查 `checkFour(…, !color)`（**对方**落此成四/成五 → 我方必防）与 `checkFour(…, color)`（**我方**落此成四 → 对方必堵）。两个半区缺一不可：只查自己方向会漏防点，只查对方方向会漏己方强制手段。

**已知限制（两版共有）**：`checkFour` 不识别"由本次落子**新形成**的 11011 型跳四"（缺口会中断连续计数）；防守对方**已有**跳四不受影响。影响的只是进攻侧一种棋形的强制展开，属可接受范围。

### 6.4 实战行为注记：防守优先是正确行为

实战曾出现"右上角已连三颗，引擎却不延伸"的疑问（第 64 手）。复盘结论：该局面黑方存在 **11011 跳四**，缺口 UI(9,7) 是黑方成五点；白方活三（UI(9,5)(10,4)(11,3)）若延伸到 UI(12,2)，黑方下一手在 (9,7) 直接五连获胜。引擎选择堵 (9,7)（分值 99700）是唯一正解——延伸自己的活三会直接输局。逐候选分值与分析图见 `move64_分析图.png`。**当对手存在成五点时，防守权重高于延伸己方棋形，这是搜索的正确行为而非漏判。**

### 6.5 回归验证

第三代算法与框架集成采用两类验证，全部通过：

- **5×5 金标准**：5×5 小棋盘 + 无剪枝完整 minimax 参照（编译期替换深度/候选数），覆盖空盘、我方活三、对方活三、跳三、对方冲四、我方冲四（短路生效返回 INT_MAX）、复杂对杀等 7 类局面，全部 PASS。
- **15×15 实战回归**（改后重跑确认）：

| 用例 | 结果 |
|---|---|
| (3,4) 冲四漏判回归：白方第 20 手应堵 (4,3) | ✓ 13.2 秒，成五短路触发 5166 次 |
| 反方向四连回归：黑四连在左侧，应堵唯一活点 (7,5) | ✓ 18.8 秒（专测反向扫描正确性） |
| 我方活三进攻：应延伸成活四（正常功能不回归） | ✓ 返回 INT_MAX（短路生效） |
| 性能基准：12 子中盘复杂局面 | ✓ 2.5 秒（修复前同类局面 2–6 秒） |

框架 v3 全模式冒烟测试通过：alphabeta / deepseek / bfs 互相执黑执白、human 落子与非法落点校验、重复落点报错、非法算法 key 忽略。

## 7. 白方算法：Minimax + α-β（DSEngine，三代框架未改动）

### 7.1 评估函数 `calcScore()`（棋形匹配）

- `extractLine`：沿方向把一条线抽成字符串：`'1'` = 己方、`'0'` = 空、`'2'` = 对方或边界墙，首尾各补一个墙字符。
- `calcScore`：棋形表逐模式匹配（含跳子识别），命中即加分并把该段替换为 `'2'` 屏蔽已计分区域，防止重复计分：

| 棋形（归纳） | 模式示例 | 分值 |
|---|---|---|
| 连五 | `11111` | 10,000,000 |
| 活四 | `011110` | 100,000 |
| 冲四族（含跳冲四） | `11110` `01111` `11011` `10111` `11101` | 10,000 |
| 活三 / 跳活三 | `01110` `010110` `011010` | 5,000 |
| 眠三维 | `001112` `211100` `010112` 等 6 种 | 1,000 |
| 活二维 | `001100` `010100` `001010` | 100 |
| 弱二 | `000112` `211000` | 10 |

- `evaluate()`：横 15 + 纵 15 + 两向对角各 29 共 88 条线，分别累计 AI 与对手分；总分 = AI 分 − **1.5** × 对手分（防守权重，源码注释："极其偏向防守"）。

### 7.2 候选生成与搜索

- `generateMoves()`：取所有已有棋子周围 2 格内的空位（去重）；空盘时下天元。
- `getBestMove()`：根候选按"离中心曼哈顿距离"升序排序（先搜中心附近，剪枝更早生效）；**迭代加深** d = 2 → 6（步进 2），即使深处超时也保有上一深度结果；`TIME_LIMIT_MS = 1500` 在根候选之间检查超时，超时立即返回当前最优。
- `minimax()`：标准 α-β 剪枝；落子即成五连直接给终局分并提前返回。
- 对外接口：`loadBoard()` 拷入对战棋盘；`getBestMovePublic()` 返回 `{x, y}`（x = 列，y = 行）。引擎内部写死执白视角（`AI_COLOR = 2`）；**v2 起执黑时由适配层翻转盘面颜色后再 loadBoard**，算法核心零改动。

## 8. 对战调度与适配说明（算法核心零改动）

三代框架遵循同一原则：算法搜索与评估逻辑未改动，只加适配层（框架内嵌副本含少量已验证勘误，见第 11 节第 1 条）。

1. **剥离 `main` + namespace 隔离**：各算法去掉入口函数，由 `Battle::step()` 统一调度；v2 起用 `BFSAlgo` / `ABAlgo` namespace 隔离两套自研算法的同名符号（`fastDict` / `getNowVal` / `DEPTH` 等）。
2. **盘面映射**：自研算法适配层把对战棋盘的 1 / 2（黑 / 白）映射成"我方 = 1 / 对方 = −1"，天然支持执黑或执白；DSEngine 写死执白视角，执黑时适配层翻转盘面颜色后再 `loadBoard`。
3. **落点提取**：BFS 版建树回溯后用 `bestBoard` 与输入棋盘做整盘 diff（恰好相差 1 格且为空）；α-β 版直接返回 `(行, 列)`。
4. **补 `deleteTree()`**：BFS 每手重建策略树，新增递归释放，防止长期对局内存泄漏。
5. **human 模式**：`step()` 的 human 分支直接采用请求携带的 `x/y`，服务端二次校验（越界 / 占位返回 `err = "非法落点"`），AI 分支校验非法着法并兜底判对方胜（正常对局不会触发）。

胜负判定在 `Battle` 层完成：五连即胜并记录获胜五连坐标供前端高亮；下满 225 手平局。

## 9. HTTP API（v3）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 对战页面（单页 HTML，随源码内嵌） |
| GET | `/api/state` | 获取当前完整状态 JSON（含双方算法配置） |
| POST | `/api/step` | 当前执方走一手（同步计算）；human 轮须带 `?x=<列>&y=<行>`，AI 轮无需参数 |
| POST | `/api/reset` | 重开一局，可选 `?black=<key>&white=<key>` 配置双方算法（`bfs` / `alphabeta` / `deepseek` / `human`；非法 key 被忽略并沿用原配置） |

**状态 JSON 结构**（实际响应中均为单行，此处展开便于阅读）：

```json
{
  "board": [[0,0,...]],        // 15×15 二维数组：0 空 / 1 黑 / 2 白，board[y][x]
  "moveCount": 2,              // 已下手数
  "lastX": 7, "lastY": 7,      // 最后一手坐标（x=列, y=行），尚无落子时为 -1
  "lastColor": 2,              // 1 黑 / 2 白，尚无落子时为 -1
  "lastMs": 15,                // 最后一手耗时（毫秒，取整；human 为 0）
  "gameOver": false,           // 对局是否结束
  "winner": 0,                 // 0 进行中 / 1 黑胜 / 2 白胜 / 3 平局
  "blackAlgo": "bfs",          // 黑方当前算法
  "whiteAlgo": "deepseek",     // 白方当前算法
  "winCells": [],              // 获胜五连坐标 [[x,y],...]，供前端高亮
  "moves": [                   // 逐手记录
    {"n":1, "c":1, "x":7, "y":7, "ms":0},
    {"n":2, "c":2, "x":7, "y":6, "ms":1583}
  ],
  "err": "非法落点"             // 仅落子失败时附加（human 无坐标 / 越界 / 占位 / 非法着法判负）
}
```

curl 示例：

```bash
curl http://localhost:8080/api/state
curl -X POST http://localhost:8080/api/step                      # AI 轮走一手
curl -X POST "http://localhost:8080/api/step?x=7&y=7"            # human 轮落子（列7,行7）
curl -X POST "http://localhost:8080/api/reset?black=alphabeta&white=deepseek"
```

## 11. 已知问题与注意事项

1. **独立版 v3 存在防点漏判（重要）**：`Gomoku_strategy_tree_v3.cpp` 第 277 行候选收集只调了 `checkFour(board, x, y, color)` 单方向，"对方落此点成四/成五（我方必防）"的威胁点未被强制进候选——实测 (3,4) 冲四漏判场景复现（落 (6,8) 而非堵 (4,3)）。修复只需一行，改成双向调用后即与框架内嵌版一致：
   ```cpp
   if (checkFour(board, x, y, !color) || checkFour(board, x, y, color)) existFour.emplace_back(x, y);
   ```
   对战框架 `Gomoku_ai_vs_ai_v3.cpp` 内嵌副本已是双向版，全部回归通过。
2. **第三代耗时特征**：正常中盘 1–5 秒/手；劣势局（几乎所有根候选都会触发对方成五短路）根层全候选需全额搜索，极端实测约 20 秒。若想提速可把 `ABAlgo::DEPTH` 降到 3，代价是看浅一层。
3. **checkFour 已知限制**：不识别"由本次落子在缺口后方新形成的 11011 型跳四"（反向/正向扫描均在第一个空位截断，跨缺口连子不计入）；缓解：该点因 aroundScore 成四加分（1e5）必进 top-15 候选，实际不影响搜索覆盖。防守已有跳四、1110 1 型成五点、反向连四均已由 v4.2 的 bcnt++ 修复覆盖。
4. **同步 API**：`/api/step` 计算期间请求持续等待，前端不要给它设置过短的超时；期间其他请求因全局互斥锁会排队等待。
5. **第一代独立版编译修复**：`Gomoku_strategy_tree.cpp` 需按第 4.3 节补 `#include <climits>` 并补全 `getNewNode` 调用参数后方可编译；对战主程序与第三代独立版无此问题。
6. **测试脚本教训**：给 `int alpha` 形参传 `long long` 初值时勿用 `LLONG_MIN`——低 32 位截断后变成 0，首轮候选会在 alpha=0 下被错误剪枝（曾导致回归脚本误报 FAIL）；请用 `INT_MIN`。
7. **端口安全**：服务监听 `0.0.0.0`，公网部署请自行增加访问控制，或改为监听 `127.0.0.1`。
8. **v4.2 修复实证（2026-11-25，实战 33 手盘面回放）**：用户实战局黑 29 手 (8,2) 后在 col=2 有跳三 (6,2)(8,2)(9,2)（成活四点 (7,2)），黑 33 手 (10,4) 再成反对角线跳三，白方第 34手下出远角废子后黑 35 手 (9,5) 成五。逐层回放结论：
   - 修复前（框架内嵌旧版 + 无兜底）：33 手后白方所有候选 INT_MIN，getBestPos 返回 (-1,-1)，走邻域兜底废子；
   - 仅加 getBestPos 兜底（用户更正版原样）：第 34 手选 (7,2) 合理堵点；但 29 手后白 (10,4) 与 col=4 已有 (6,4)(7,4)(8,4) 构成 1110 1 跳四，因 checkFour 反向连子恒为 0（bcnt 未累加），黑方堵 (9,4) 的着法进不了 existFour，搜索把 (10,4) 误判为 INT_MAX 幻胜，白 30 手会"自信地"下 (10,4) 送掉主动权；
   - 补 bcnt++ 后：(10,4) 降为 98040，白 30 手选 (5,2) 真堵跳三（99440 全场最高），32 手 (9,4)（强制反四），34 手 (7,2)（必败兜底），INT_MIN 仅出现在真必败点。
   - 第四代劣势局耗时实测更新：中盘单手最高约 36 秒（DEPTH=4 全宽 + existFour 全展开，根层候选全部触发对方成五短路时最慢），网页自动对局建议把间隔调大或改用单步模式。
